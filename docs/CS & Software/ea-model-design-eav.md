# 数据模型之 EAV ｜ 灵活、快速地构建业务的属性存储 

## 1.什么是 EAV 
EAV（Entity-Attribute-Value，实体-属性-值）模型是一种灵活的数据库设计模式，通过将数据拆分为实体表、属性表和值表，实现自定义属性的存储与管理。其核心思想是将传统表中“列”的固定属性转化为“行”的动态记录，从而支持无限扩展的异构数据。

我觉得使用这个模式最成功的应用莫过于 WordPress 了 ，其元数据系统（如wp_postmeta表）正是EAV模型的典型应用。例如，一篇博客文章（实体）的元数据（如作者、标签、自定义字段）通过 meta_key（属性）和 meta_value（值）动态存储，无需修改核心表结构即可支持插件扩展。

对一个实体，例如一个客户表 customer, 通常我们这么表示：

| id    | name | birthday | ... |
| ----- |------ |------ | ----- | 
| 1 | John | 2002-09-23 |
| 2 | Alan | 1993-02-03 |

而用 EAV 侧是分为元信息和值来分别存储：
**entity_meta**

| id    | name | fields | 
| ----- |------ |------ |
| 1 | customer | [{"key":"name", "type":"string", "key":"birthday", "type":"date"}] |


** field_value**

|id|entity_id| field_key|meta_value|
| -------- |------ |------ | ------ | 
|1|	1|name|John|
|2|	1|birthday|2002-09-23|
|3|	2|name|	Alan|
|5	|2|birthday|1993-02-03|


## 2. EAV 模型的特点与一般实践

从上面的表可以看出来它的适应性是很强的，假如你需要为这个表增加一个 age 字段，都不需要去改动表结构，只需要修改表记录，所以它具有很强的`动态扩展性`​。

假如我们面对的用户是多样的，有些有些公司的客户需要 age ,有些公司业务只需要 title 职位不需要 age , 那么如果要设计一个都对他们适用的表的话，传统的方式既要有年龄又要有性别，所以这又引入了数据稀疏的问题，因为关系数据库的设计，很多空间是浪费的了，所以单纯从这个角度看，它有 `比较好的存储效率`，当然，因为需要更灵活的存储，所以通常 meta_value 会被设计成 varchar 变长字段，应对更长的内容需要，这个点后面会继续讨论。

以上在项目的初期，因为需求可能也在快速的变化，数据的体量也比较小，所以使用它可以跟让业务开发比较敏捷。 

我们可以很轻易地想到他的缺点也很明显，甚至让人无法接受。
当我们要查询一条 customer 时还可以接受，`select * from field_value where entity_id=2;` 

当需要查询一个当是一个列表的时候，就比较麻烦了，如何过滤出全部的 customer 类型？ 往 field_value `entity_type` 属性？好像可以，就算是数据体量小，灵活很好的 wordpress 也不会这么实践。

一般的实践，将核心固定字段（如文章标题）存储在传统表中，自定义属性通过EAV扩展。例如，WordPress的 wp_posts 表存储文章等各类自定义内容（conten-type）的基础信息，而wp_postmeta仅处理扩展字段。
那么设计就变成：

**entity_value**

| id    | name | parent_id | entity_type | create_by| update_by| create_at | last_update|
| ----- |------ |------ |---- |---- |---- | --- | --- |
| 1 | John| 0 | customer | xx | xx | xx | xx | 
| 2 | Alan | 0 | customer | xx | xx | xx | xx | 

其他的比较动态化的属性，仍然放在 field_value，这个结构，这是应对万级业务实体的场景，已经足够了。

适用阶段：
​业务初期：需求尚未稳定，需快速试错。
​自定义属性场景：属性频繁变化或高度异构

如果某个实体数据量比较多，那么可以把实体表就分离出来，动态的属性值也相应可以考虑分离出来，就有了 customer, customer_field_value，这样也可以做到实体的核心业务放到核心表里面。这个做法牺牲一定的灵活性，但兼顾了性能。从业务的角度看，也可以说这个业务完成了成长或者一开始就是关键的，所以需要独立出来，到此我完成 10w~1000w 级别的应用场景。

可能大部分的技术的文章来讲讲到这里就结束了，而且动态的属性是不是不能参与过滤？难道要加一个属性，且可以过滤就要修改 entity 的表结构吗？把一个属性变成可筛选，就得迁移数据？
我们的目标要构建中大型的企业应用的，所以我们继续。

## 3. 进阶，EAV 的企业级实践
先思考几个问题：

1. entity_value 表如何结合实体表和其他表做复杂查询
2. 把所有的数据类型都变成 varchar 格式的方式如何写过滤条件，编码实现类型转换？
3. 不管是在内存中或者是在数据库中过滤，它的性能如何保障？

当然，如果领域的抽象可以固定在实体表的属性，以上的问题可能不需要回答，或者数据体量比较小，field_value 加载到内存里转换计算，勉强也能接受。

讨论这个问题比较难，因为它可能和业务类型有关、和技术投入有关、和软件的分层及抽象有关，我们分为多个阶段来解决。

#### 解决类型问题
一个字期和一串字符，是不能比较大小的，也没有意义。
所以我们在存储上，可以牺牲一定的空间，来换取运算操作的可能性。
改进方式是把 field_value 值分为几种类型来存储。
** field_value**

|id|entity_id| field_key| string_value| number_value | text_value | date_value |
| -------- |------ |------ | ----- | --- | --- | --- |
|1|	1|title| PM | |
|2|	1|birthday| | ||2002-09-23|
|3|	2|title| UI Designer |
|5	|2|birthday| | ||1993-02-03| 
|5	|2| age | | 23 ||| 

我们先来分析一下这个的表达结构， string 是 varchat 变长的, number 是 bigint, 有一定的空间浪费，text 数似 varchat 大文本时记录外存储，date 是个数字和 number 类似。

相应地，我们需要改进 fields 的存储，因为读不同的属性值行为差异化了，所以需要给它增加一个 type 字段，用来区分读数据和转换数据行为。
考虑到管理属性的便捷性，还有 entity 表的独立，都让我们不得不把 fields 独立存储，属性作为元信息，数据量也相对少，把所有实体的自定义属性 field 一起存储。

**custom_field**

|id|entity_type| key| label| field_type | 
| -------- |------ |------ | ----- | --- | 
|1|	customer | title| 职称 | | string
|2|	customer |birthday| 生日 | date |
|5| customer | age | 年龄 | int |

做到这个程度，我们回顾刚刚的问题，1, 2，3 点某种程度解决了，但好像没有完全解决，好像写 sql 比较难。
其实使用这类方案已经不适于用手写 SQL 的方式去查询数据，我们的实践是，上层的条件传下来，dao 层需要结合 custom_field 的元信息，经过一层数据类型的判断，然后再生成相应的 SQL。

> [!NOTE] 工程化
> 通常来讲，一个企业级的应用，我们描述好实体后，实体的 dao 数据访问层和代码的数据结构应该由工具生成，如果不是那代表着可能应该就这方面去做抽象，或者就算是实体较少，还没有工具化，那么 model 层的代码也行为也是应该一致的。

## 结语
EAV模型如同一把双刃剑：它为动态业务提供了无限可能，却也带来了性能与复杂度的挑战。我们探讨了在具体的项目实践中，怎么样在关系型数据库中去利用它的特性，用例子说明了灵活和性能如何平衡。当然这里也可以继续扩展下去，进一步实现一个通用化的 实体-属性-值 的 dao 层，基础的有查询、更新，删除。后面有机会再继续讨论。
